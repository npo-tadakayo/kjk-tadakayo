§0 これは何のシステム？

介護事業所の「介護情報基盤」導入を、NPO法人タダカヨが伴走支援する事業の管理システムです。LP・見積もりツールからの問い合わせを案件として受け取り、担当・伴走支援・助成金申請・カードリーダーの発注/在庫/出荷までを一元管理します。

§5 認証・セキュリティ

  • 管理画面: Googleログイン＋@tadakayo.jp 限定（Firestoreルールで強制）
  • 認定事業者ポータル: Googleログイン＋許可リスト（partners）。自分の発注のみ閲覧
  • メール送信: ドメイン全体委任（DWD）・キーレス（鍵を保存せず都度署名）。スコープは gmail.send のみ
  • AI: Vertex AI + SA認証（裸APIキー不使用）

§7 供給・請求の単価と送料（2026-06 統合）

RULE｜出荷の単価・送料の決まり方
  • 認定事業者への直送(dropship): 単価は appConfig.settings.partnerPricing（台数帯別: 1台 / 2〜10台 / 11〜30台 / 31台〜）を使用。未設定時は商品マスタの卸へフォールバック。
  • 事業所への直接出荷(direct): 単価はエンドユーザー定価（products.listPrice）。
  • 送料: 配送方法で自動計算 — レターパック=letterpackFee × ⌈総台数/3⌉ ／ ゆうパック=yupackTable[サイズ][地域]（滋賀発）。shipments.shippingFee/shippingMethod/shippingLabel に保存。shippingFee は税抜で保存する（2026-07-28 統一。発注側の送料欄が元から「税別」だったのに揃えた）。料金表は税込の実費なので、自動入力時に ÷1.1 して税抜に換算する。請求書・領収書は税抜のまま明細に載せ、消費税は小計に対して1回だけ計算する（インボイス制度の端数処理）。
  • 請求書: 送料(税込実費)を税抜換算し、商品と合算して10%課税（適格請求書の明細に1行計上）。
  • 直送発注の自動出荷（2段階）: 発注(purchaseOrders)で「直送する」指定時、発注確定で shipments を status=draft で自動生成（shipType=dropship・fulfillment=direct・単価=認定事業者卸・在庫は経由しない・発注に shipmentId 記録で二重防止）。出荷タブで draft →「出荷を確定」で shipped（在庫を動かさず）→ 請求書/送付状。請求先は常に認定事業者。
  • 領収書（2026-07 追加）: 入金済み出荷（status=paid）に対し supply-print.html?type=receipt で発行。発行元・登録番号・角印は請求書と共通（印影は settings.poSealImage、無ければ images/seal-tadakayo.png）。明細は画面上で編集・行追加でき、各行の用途区分 A=カードリーダー / B=接続サポート等経費 / X=対象外(送料等) ごとに税抜/消費税/税込小計を自動再計算。税込5万円以上で収入印紙欄を表示。
  • 入金（2026-07-30 部分入金対応）: shipments.payments[] = {amount(税込), date, note, recordedBy, recordedAt} に履歴で積む。合計は paymentAmount にも同期（旧フィールド互換）。旧形式（paymentAmount+paidAt）は1件の履歴として読み替え。残額>0 は invoiced のまま（一部入金）／残額≤0 で paid＋paidAt=最終入金日。入金の取消も同じ判定で自動的に巻き戻す。
  • 返金・複数回入金（2026-08-01 追加）: shipments.refunds[] = {amount,date,method,note,recordedBy,recordedAt}。判定はすべて純入金 netPaid = 入金合計 − 返金合計（payRemain・overpayOf・サマリー・受注タブ）。旧フィールドは paymentAmount=純額・refundAmount=返金合計で同期。過入金の返金で creditBalanceOf は0（次回請求へ回さない）。請求額まで返金すると paid→invoiced に戻る（取引取消は出荷削除＝在庫も戻す）。入金は payments[] に何回でも追記でき、入金と返金は日付順にマージして純入金の累計を表示・個別に取消可。二重入金は「満額×2」＝過入金として①充当②返金で解消。
  • 過入金の充当（2026-08-01 追加）: 請求額超過の入金は返金せず次回請求へ充当。billableIncl = 税込合計 − creditApplied（充当後の請求額）／payRemain = billableIncl − 入金合計／overpayOf = 入金合計 − billableIncl／未充当残高 creditBalanceOf = overpayOf − overpayUsed。充当先に creditApplied と creditFrom[{shipmentId,soNumber,amount,date,appliedBy}]、充当元に overpayUsed を記録。請求先の同一判定は billToKey()（直送=partnerEmail／直接=companyorofficeName）、古い shipDate の過入金から FIFOで min(請求先の未充当残高, 残額) を充当（引ききれない分は残高として次回へ）。充当で残額0なら paid。請求書は税込合計の下に「前回お預かり分の充当 −¥X」＋「今回お支払額」を出す。
  • 未集金（2026-07-30 追加）: 支払期限 dueDateOf() = shipments.dueDate 優先、無ければ請求月（invoicedAt→shipDate）の翌月末（請求書の記載と一致）。overdueDays() が超過日数。未集金の定義は status==="invoiced" && 残額>0（発送済・未請求は別カウント）。請求先ごとに集約表示し、受注タブは partnerOrderId 経由で残額を表示。
  • 充当元の明示選択・グループ会社間の充当（2026-08-12 追加）: 充当は openCreditModal() → doApplyCredit() の2段階で充当元を人が選ぶ方式に変更。creditSourcesFor()（同一 billToKey）は既定チェック済み・古い順に残額を埋める金額を自動入力＝従来と同じ結果。新設 crossCreditSourcesFor() / crossCreditBalanceFor() が別請求先の未充当過入金を返し「別請求先」バッジ付きで並ぶが既定オフ・金額欄 disabled、選択時は confirm() 必須。creditFrom[] に fromBillTo・crossBillTo を追加保存し、請求書は crossBillTo があると充当行に「（SO番号／請求先名様 の過入金）」を印字。バリデーションは合計>0／合計≤残額／各行≤creditBalanceOf(充当元)。「請求済にする」直後の自動サジェストは同一請求先のみ（グループ間は自動提案しない）。
  • 返金明細書（2026-08-12 追加）: supply-print.html?type=refund&id={shipmentId} → renderRefundStatement()。番号は SH→RFND。返金全件（日付・方法・摘要・金額）＋内訳（ご請求金額／ご入金額／返金額／差引後）。領収書ではない旨を書面に明記（当方が支払う側＝印紙不要）。「発行を記録」で出荷側に refundStatementNo/refundStatementIssuedAt/refundStatementIssuedBy/refundStatementAmount を保存（返金内容の正本は refunds[] のままで別コレクションは作らない）。一覧のボタンは refundSum(s)>0 のときだけ表示。
  • 領収金額に実入金を自動反映（2026-08-12 追加）: 領収金額は明細合計の従属値ではなく、初期値 min(netPaid, billableIncl)（過入金は含めない／一部入金はその額）。#rcptGrand=明細合計・#rcptTotal=領収金額に分離し、#rcptAmountInput（印刷非表示）で上書き可＋「実入金に戻す」「明細合計に合わせる」。収入印紙の5万円判定も領収金額基準。一部入金なら但し書きの既定が「〜の内金として」に変わり、#rcptAdjNote に不足理由（充当分→内金分の順）を印字。帳票側は Firestore を読まず payListOf/netPaidOf/billableInclOf を supply-print.js 内に持つ（税込計算 sub+floor(sub*0.1) を変えるときは supply.js と両方直す）。スナップショットに itemsTotalIncl・netPaid・billableIncl・isPartial を追加。
  • 領収書の発行記録（2026-07-30 追加）: receipts/{shipmentId} に receiptNo（出荷番号の SH→RCPT 置換＝既発行の紙と整合）・issuedAt・amountIncl・note・items[{usage,name,qty,unitPrice}]・usageTotalsIncl{A,B,X} をスナップショット保存し、出荷側に receiptNo/receiptIssuedAt/receiptIssuedBy/receiptAmountIncl を書き戻す。再表示時は保存内容を復元（同内容で再発行・発行日も保存値）。
  • 催促メール（2026-07-30 追加）: callable sendPartnerMail（sendSupplierOrder と同じ SA_MAIL / DWD キーレス / gmail.send）。送信成功で shipments.mailLog[] に追記し、kind==="dunning" なら dunningSentAt・dunningCount を更新。文面の既定は supply.js の DEFAULT_DUNNING_SUBJECT/BODY、settings.dunningMailSubject/Body で上書き可。
  • 経理への請求書発行報告（2026-08-11 追加）: 「請求済にする」で確認ダイアログが開き、経理へ報告する（既定ON・既報告済みならOFF）で送信可否を選ぶ（再発行のときは外す）。callable reportInvoiceToAccounting（SA_MAIL）が ①PDFを Storage invoices/{shipmentId}/ に保存 ②経理へPDF添付メール（Gmail DWD）③経理スペースへ Chat cardsV2 投稿（PDFリンク＋CRMリンク＋「〇〇さんにもメールを送信しました」）④出荷に accountingReportedAt/By・accountingReportLog[]・invoicePdfUrl を記録。⚠️ Google Chat の Incoming Webhook はファイルを添付できない（添付の media.upload はユーザーOAuth認証のみ対応でSA・Webhookは不可）ため、PDF本体はメール添付・ChatはPDFリンクで代替している。設定（Webhook URL・経理メール・呼び名・CC・メール定型文）はすべて「設定」画面から変更可。片方が失敗しても他方は続行し、請求済の行の「経理へ報告」ボタンで後追い報告できる。
  • 請求書描画の共通化（2026-08-11 追加）: admin/js/invoice-doc.js（po-doc.js と同じ役割）に renderInvoiceHtml／INVOICE_STYLE／invoiceNoOf／invoiceTotals を集約。supply-print.js の renderInvoice はこれに委譲し、supply.js は経理報告のPDF生成に同じ関数を使う（印刷とPDFで見た目がズレない）。報告する金額は一覧と同じ billableIncl() を正とする。
  • 発注の下書き戻し・直送の入荷抑止（2026-07-30 追加）:発注済(sent)→draft に戻す操作（revertedAt/revertedBy 記録・入荷済は対象外）。dropship=true の発注には「入荷登録」を出さない（自社在庫を経由しないため誤加算を防ぐ）。発注の送料自動入力は総数量100台以上で0円（AB Circle は1便100台以上が無料）。
