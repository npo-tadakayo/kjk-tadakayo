# 倉庫用メニュー 設計案（2026-10-24・案・未実装）

次田さんの問い（2026-10-24）:「保管場所ごとに保管の状況が確認できる画面があるか？ 出荷指示と処理状況を確認・登録できる倉庫用のメニューがあってもよいと思うがどう考えるか」への答えと、作る場合の設計。

## 1. いまの状況（実コードで確認）

| 知りたいこと | 今 | 場所 |
|---|---|---|
| 保管場所ごとの在庫 | ✅ ある（商品ごとに場所別の台数＋移動中） | 在庫・発注 →「在庫・商品」タブ（`products.stockByLocation`） |
| 保管場所ごとの出荷依頼と処理状況 | ❌ 専用画面なし。全部の出荷が1つの一覧。出荷元は依頼時に選ぶが、場所での絞り込み・場所ごとの待ち件数はない | 在庫・発注 →「出荷」タブ |
| 倉庫の担当者向けの入口 | ❌ なし。供給管理の画面全体（発注・受注・料金まで）が見える | — |
| 出荷指示の伝え方 | Chat（OP_出荷依頼）への自動投稿のみ | `notifyShipment` |

## 2. 結論（推奨）

**作る。ただし倉庫の担当者には「自分の場所の出荷」だけを見せる専用画面にする。**
理由: ①倉庫側は発送の記録だけが仕事で、金額・事業所の個人情報・案件は要らない（Pマーク準備中の最小権限）。②今は Chat の投稿が流れて「依頼済みのまま残っている出荷」が追えない。③在庫引き落としが「発送済にする」で行われるため、押す人（倉庫）と画面が一致している方が事故が減る。

## 3. 画面（`/warehouse`）

- 上部: 保管場所の選択（自分に割り当てられた場所のみ。1つなら固定）。待ち件数のバッジ。
- タブ3つ
  1. **出荷依頼**（status=requested・出荷元＝選択中の場所）: 古い順。1行に 出荷番号／宛先名・住所・電話／品名×数量／希望出荷日／レターパック種類／依頼者・依頼日時／メモ。
     - ボタン「**発送済にする**」→ 発送日・追跡番号（任意）・レターパック種類を確認 → 登録。
     - ボタン「**出荷できない**」→ 理由（在庫不足・住所不備・その他）を入れる → 依頼者へ Chat 通知。状態は依頼済のまま、行に「倉庫から差し戻し」を表示。
  2. **発送済**（直近30日・訂正用に追跡番号だけ直せる）
  3. **在庫**（選択中の場所の商品別台数・読み取りのみ。入荷／棚卸／移動は第2段階）
- 印刷: 宛名ラベル・レターパック（既存の `letterpack-print` を再利用）。

## 4. 権限とデータの守り方（ここが設計の核心）

- 新ロール **`warehouse`**。`users/{email}` に `locationIds: ["…"]`（扱える保管場所）を追加。
- **warehouse には Firestore を直接読み書きさせない。** 既存の `isRegistered()` に通ると全コレクション（案件・事業所＝個人情報）が読めてしまうため、trainee と同様に `isRegistered()` から除外する（自分の `users` 文書だけ読める）。
- 倉庫画面のデータは **Callable Functions 経由**にする（サーバー側で `locationIds` を検証し、必要な項目だけ返す）。
  - `warehouseList({locationId})` → 出荷依頼・発送済・在庫を、金額・案件ID・事業所の他情報を除いて返す
  - `warehouseShip({shipmentId, shipDate, trackingNumber, letterPackType})` → 既存と同じトランザクション（依頼済のままか確認・在庫を出荷元から引く・shippedBy 等の印）をサーバーで実行。**在庫ロジックは `supply-rules.js` / `ship-flow.js` の関数を Functions 側で共有**（二重実装しない）
  - `warehouseReject({shipmentId, reason})` → 理由を記録し Chat 通知
- 画面側: `gateRole` が warehouse を `/warehouse` だけに誘導。サイドバーは倉庫メニューのみ。他URLを直接開いても拒否画面。
- 練習モード: 練習生は従来どおり。倉庫画面の練習は `practice-stubs.js` に3つの callable を足す（第2段階でよい）。

## 5. 既存への影響と注意

- 出荷の状態遷移（draft→requested→shipped→invoiced→paid）は**変えない**。発送済にする経路が1つ増えるだけ（ship-flow.js が正本）。
- 出荷元の保管場所が未設定の古い出荷は、既定の場所扱い（既存 `shipLocationOf` と同じ）。
- Chat（OP_出荷依頼）の投稿は残し、文末に倉庫画面へのリンクを足す。
- 直送（`fulfillment: direct`）は倉庫を通らないので倉庫画面に出さない。

## 6. 段階

| 段階 | 内容 | 目安 |
|---|---|---|
| 1 | warehouse ロール・`/warehouse`（出荷依頼＋発送済にする＋出荷できない・在庫の閲覧）・3つの callable・ルール・テスト | 中（権限の変更を含むので Opus 推奨・本番は Functions→rules→Hosting の順） |
| 2 | 入荷登録・棚卸・場所間の移動・練習モード対応 | 小〜中 |
| 3 | 滞留アラート（依頼から2営業日超で担当へ通知）・倉庫の週次サマリ | 小 |

## 7. テスト計画（段階1）

- ルール: warehouse が cases / offices / quotes を読めない・書けない／自分の users は読める
- callable: 他の場所の出荷を取得・発送できない／依頼済でない出荷は発送できない／在庫不足は止まる／二重押しで在庫が二重に引かれない／返す項目に金額・案件IDが無い
- 画面: 1場所だけのアカウント・複数場所のアカウント・viewer／staff が倉庫画面を開いたときの扱い
- 既存回帰: 15本の単体テスト＋出荷フロー（依頼→発送済）が従来どおり
