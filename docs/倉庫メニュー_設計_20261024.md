# 倉庫用メニュー 設計案（2026-10-24・案・未実装）

次田さんの問い（2026-10-24）:「保管場所ごとに保管の状況が確認できる画面があるか？ 出荷指示と処理状況を確認・登録できる倉庫用のメニューがあってもよいと思うがどう考えるか」への答えと、作る場合の設計。

## 1. いまの状況（実コードで確認）

| 知りたいこと | 今 | 場所 |
|---|---|---|
| 保管場所ごとの在庫 | ✅ ある（商品ごとに場所別の台数＋移動中） | 在庫・発注 →「在庫・商品」タブ（`products.stockByLocation`） |
| 保管場所ごとの出荷依頼と処理状況 | ❌ 専用画面なし。全部の出荷が1つの一覧。出荷元は依頼時に選ぶが、場所での絞り込み・場所ごとの待ち件数はない | 在庫・発注 →「出荷」タブ |
| 倉庫の担当者向けの入口 | ❌ なし。供給管理の画面全体（発注・受注・料金まで）が見える | — |
| 出荷指示の伝え方 | Chat（OP_出荷依頼）への自動投稿のみ | `notifyShipment` |

## 2. 結論（推奨）

**作る。ただし倉庫の担当者には「自分の場所の出荷」だけを見せる専用画面にする。**
理由: ①倉庫側は発送の記録だけが仕事で、金額・事業所の個人情報・案件は要らない（Pマーク準備中の最小権限）。②今は Chat の投稿が流れて「依頼済みのまま残っている出荷」が追えない。③在庫引き落としが「発送済にする」で行われるため、押す人（倉庫）と画面が一致している方が事故が減る。

## 3. 画面（`/warehouse`）

- 上部: 保管場所の選択（自分に割り当てられた場所のみ。1つなら固定）。待ち件数のバッジ。
- タブ3つ
  1. **出荷依頼**（status=requested・出荷元＝選択中の場所）: 古い順。1行に 出荷番号／宛先名・住所・電話／品名×数量／希望出荷日／レターパック種類／依頼者・依頼日時／メモ。
     - ボタン「**発送済にする**」→ 発送日・追跡番号（任意）・レターパック種類を確認 → 登録。
     - ボタン「**出荷できない**」→ 理由（在庫不足・住所不備・その他）を入れる → 依頼者へ Chat 通知。状態は依頼済のまま、行に「倉庫から差し戻し」を表示。
  2. **発送済**（直近30日・訂正用に追跡番号だけ直せる）
  3. **在庫**（選択中の場所の商品別台数・読み取りのみ。入荷／棚卸／移動は第2段階）
- 印刷: 宛名ラベル・レターパック（既存の `letterpack-print` を再利用）。

## 4. 権限とデータの守り方（ここが設計の核心）

- 新ロール **`warehouse`**。`users/{email}` に `locationIds: ["…"]`（扱える保管場所）を追加。
- **warehouse には Firestore を直接読み書きさせない。** 既存の `isRegistered()` に通ると全コレクション（案件・事業所＝個人情報）が読めてしまうため、trainee と同様に `isRegistered()` から除外する（自分の `users` 文書だけ読める）。
- 倉庫画面のデータは **Callable Functions 経由**にする（サーバー側で `locationIds` を検証し、必要な項目だけ返す）。
  - `warehouseList({locationId})` → 出荷依頼・発送済・在庫を、金額・案件ID・事業所の他情報を除いて返す
  - `warehouseShip({shipmentId, shipDate, trackingNumber, letterPackType})` → 既存と同じトランザクション（依頼済のままか確認・在庫を出荷元から引く・shippedBy 等の印）をサーバーで実行。**在庫ロジックは `supply-rules.js` / `ship-flow.js` の関数を Functions 側で共有**（二重実装しない）
  - `warehouseReject({shipmentId, reason})` → 理由を記録し Chat 通知
- 画面側: `gateRole` が warehouse を `/warehouse` だけに誘導。サイドバーは倉庫メニューのみ。他URLを直接開いても拒否画面。
- 練習モード: 練習生は従来どおり。倉庫画面の練習は `practice-stubs.js` に3つの callable を足す（第2段階でよい）。

## 5. 既存への影響と注意

- 出荷の状態遷移（draft→requested→shipped→invoiced→paid）は**変えない**。発送済にする経路が1つ増えるだけ（ship-flow.js が正本）。
- 出荷元の保管場所が未設定の古い出荷は、既定の場所扱い（既存 `shipLocationOf` と同じ）。
- Chat（OP_出荷依頼）の投稿は残し、文末に倉庫画面へのリンクを足す。
- 直送（`fulfillment: direct`）は倉庫を通らないので倉庫画面に出さない。

## 5.5 送付方法「持ち出し」（2026-10-24 次田さん追加の要望）

> 送付方法を追加したい。送付指示の他に持ち出しがほしい。倉庫から直接持っていくということ。

**いま**: 出荷の流れは「出荷を依頼する（出荷指示を OP_出荷依頼 へ投稿）→ 発送済にする（在庫を引く）」の1本だけ。送料の欄に「郵送なし（手渡し・持参）」（`shippingMethod:"none"`）はあるが、これは**送料の計算のための区分**で、倉庫への指示の中身・記録は発送と同じ（レターパック・追跡番号を聞く）。

**案**: 出荷を依頼するときに **送付方法** を選ぶ。

| 送付方法 | 倉庫への指示 | 倉庫で押すボタン | 記録 |
|---|---|---|---|
| **発送**（今まで） | 「〇〇へ発送してください」・レターパックの種類 | 発送済にする（追跡番号） | 発送日・追跡番号・発送した人 |
| **持ち出し**（新規） | 「〇〇さんが △日に取りに行きます」・持ち出す品と数 | **受け渡し済にする** | 受け渡した日・**持ち出した人**・受け渡した倉庫の人 |

- データ: 出荷に `deliveryMode: "ship" | "pickup"`（未設定は "ship"＝今までどおり）。持ち出しは `pickupBy`（持ち出す人のメール・CRM の利用者から選ぶ）・`pickupDate`（予定日）、受け渡し後に `handedOverAt`・`handedOverBy`。
- 状態の流れは同じ（下書き → 依頼済 → **受け渡し済＝発送済と同じ扱い** → 請求済 → 入金済）。**在庫は受け渡した時点で倉庫から引く**（発送済と同じ）。請求・入金の流れは変えない。
- 持ち出しを選ぶと、送料は自動で「郵送なし（手渡し・持参）」にし、レターパック・追跡番号は聞かない。
- 出荷指示の Chat 投稿は文面を変える（【持ち出し】〇〇さん・△日・品と数・保管場所）。持ち出す本人にもメンションする。
- 倉庫画面（§3）の「出荷依頼」タブに、発送と持ち出しを並べて出す（持ち出しには印。予定日の近い順）。
- 事業所に届けたことの記録（訪問のときに渡した）は、案件の対応記録で残す（今回は新しい欄を作らない）。

**決めてほしいこと（推奨つき）**
- A. 在庫を引くのは「倉庫で受け渡したとき」でよいか → 推奨: はい（倉庫の棚から減った時点。持ち出した人の手元にある間も「出荷済み」として数える）
- B. 持ち出す人は CRM の利用者から選ぶ形でよいか → 推奨: はい（Chat でメンションでき、記録が名前の揺れなく残る）
- C. 持ち出しは**倉庫画面より先に**作るか → 推奨: はい。今の「出荷・請求・入金」画面に送付方法を足すだけで先に使える（倉庫画面は後から同じデータを読む）

## 9. 確定設計（2026-10-24 次田さん「倉庫の機能を作って」・§8 と §5.5 の A〜C はすべて推奨どおり）

### 9.1 権限（いちばん大事）
- 新ロール **`warehouse`（倉庫）**。`users/{email}` に `locationIds: string[]`（扱える保管場所）。倉庫の人は @tadakayo.jp。
- ⚠️ 現状の判定は「閲覧のみ以外は書ける」（`Flow.roleAllows(user,"editor")` = `role !== "viewer"`、rules の `isEditor()` も同じ）。**このまま足すと倉庫の人が全 Callable・全コレクションを書けてしまう**。次のとおり直す:
  - `roleAllows`: `warehouse` は `"viewer"`／`"editor"`／`"admin"` のどれも通さない（倉庫用の新しい指定 `"warehouse"` だけで通す）。
  - rules `isRegistered()`: trainee と同じく **warehouse を除外**（自分の `users` 文書だけ読める。他は Firestore を直接読めない）。
  - 倉庫の画面のデータはすべて **Callable 経由**（サーバーで `locationIds` を確かめ、必要な項目だけ返す）。
- 管理者・スタッフも倉庫画面を使える（全保管場所）。閲覧のみ・練習生は使えない。
- 画面: `gateRole` が warehouse を `/warehouse` 以外から `/warehouse` へ移す。サイドバーは倉庫だけ。練習モードの切り替えは出さない。

### 9.2 送付方法（§5.5）
- 出荷に `deliveryMode: "ship"|"pickup"`（未設定＝"ship"）。依頼のとき選ぶ。
- 持ち出し: `pickupByEmail`・`pickupByName`（CRM の利用者から選ぶ）・`pickupDate`（YYYY-MM-DD）。送料区分は自動で `shippingMethod:"none"`。レターパック・追跡番号は聞かない。
- 受け渡し: 状態は `shipped`（発送済と同じ扱い・在庫はここで出荷元から引く）。`shipDate`＝受け渡し日、`handedOverAt`・`handedOverByEmail`・`handedOverByName`（受け渡した倉庫の人）。`shippedBy*` は従来どおり押した人。
- スタッフ画面: 依頼の確認に「送付方法」（発送／持ち出し）。持ち出しの依頼済には「受け渡し済にする」（発送済にするの代わり）。「すでに発送済（記録のみ）」は持ち出しなら「すでに受け渡し済（記録のみ）」。一覧に「持ち出し」の印と予定日・持ち出す人。
- 出荷指示（notifyShipment の Chat 文面）: 持ち出しは【持ち出し】・持ち出す人（メンション）・予定日・保管場所・品と数。発送は従来どおり。どちらも倉庫画面へのリンクを末尾に。

### 9.3 倉庫からの差し戻し「出荷できない」
- `warehouseIssue: {reason:"shortage"|"address"|"other", note, at, byEmail, byName}`。状態は依頼済のまま。依頼した人（`requestedByEmail`）に Chat でメンション（出荷指示と同じ投稿先）。
- スタッフ画面の行に「倉庫から：〇〇」と出す。スタッフが「依頼を取り消す」か依頼し直すと消える。倉庫の人が「発送済」「受け渡し済」にしたときも消える。

### 9.4 Callable（すべて asia-northeast1・倉庫の人か管理者・スタッフ。保管場所の権限をサーバーで確認）
| 名前 | 入力 | 内容 | 戻り値 |
|---|---|---|---|
| `warehouseList` | `{locationId}` | その場所の依頼済（発送・持ち出し）・直近30日の発送済/受け渡し済・在庫 | `{location:{id,name}, locations:[{id,name}], requested:[W], done:[W], stock:[{sku,name,qty}]}` |
| `warehouseShip` | `{shipmentId, shipDate, trackingNumber?, letterPackType?}` | 発送の依頼済→発送済。在庫を出荷元から引く（足りなければ止める）。トランザクション | `{ok:true}` |
| `warehouseHandover` | `{shipmentId, date}` | 持ち出しの依頼済→受け渡し済。在庫を引く | `{ok:true}` |
| `warehouseReject` | `{shipmentId, reason, note}` | 「出荷できない」を記録して依頼した人へ通知 | `{ok:true, notified:boolean}` |
| `warehouseFixTracking` | `{shipmentId, trackingNumber}` | 直近30日の発送済の追跡番号だけ直す | `{ok:true}` |
- W（倉庫に返す出荷の形・**これ以外は返さない**＝金額・案件ID・請求の情報を出さない）: `id, soNumber, status, deliveryMode, officeName, company, contactName, postalCode, address, phone, items[{sku,name,qty}], desiredDate, letterPackType, note, requestedByName, requestedAt, pickupByName, pickupDate, warehouseIssue, shipDate, trackingNumber, handedOverAt, handedOverByName`。
- 在庫を引く処理は supply.js の「発送済にする」と同じ結果になること（`stock` と `stockByLocation.{loc}` を同時に・`stockMovements` に理由と参照番号・`shippedBy*`・`dueRule:"net14"`）。
