# 設計：出荷に「伴走支援費」を任意の金額で入れられる行（2026-11-09・設計のみ／未実装）

## 1. 背景（なぜ要るか）
- ナガヨシ様の残り1件：カードリーダーは先方購入済みで 0台。請求は「助成金上限 − 先方のリーダー購入費」を伴走支援費（サポート費）として ¥30,200 の1行だけ。
- 今の出荷モーダルの「伴走支援費を含める」はプラン＋台数から自動計算で、金額を自由に入れられない。申込フォームも 0台では申し込めない。
- 領収証の明細は編集できるが、請求書にはその機能がない。

## 2. 決まっている方針（次田さん 2026-11-09）
1. 伴走支援費を**任意の金額で入れられる行**を足す。
2. **自動の伴走支援費の行がすでにあるときは、任意行を追加できない**（二重計上の防止）。
3. ゼロから作る（既存の自動計算の仕組みは変えない）。

## 3. 設計

### 3.1 データ（出荷 `shipments/{id}.items[]`）
自動行と**同じ sku `support-fee`** を使い、印を1つだけ足す。

```
{ sku:"support-fee", name:"伴走支援費", qty:1, unitPrice:<税込・整数円>, nonStock:true, manual:true }
```

- 自動行は `manual` なし。任意行は `manual:true`。
- 同じ sku を使う理由：請求書のB区分（supply-print.js:194,634）、在庫を動かさない扱い（ship-flow.js:248、warehouse-rules.js:140、functions/index.js:2767,2774）、請求書の文言（invoice-doc.js:91）が**すべてそのまま効く**。新しい sku にすると、これらを全部直す必要がある。
- 品名は初期値「伴走支援費」。変えられるが、空にはできない。

### 3.2 排他ルール（「自動があれば追加不可」）
- 出荷の items に **`support-fee` が1行でもあれば、任意行は追加できない**（自動・任意どちらでも）。つまり伴走支援費の行は**最大1行**。
- 画面：
  - 「伴走支援費を含める（助成金の上限までの構成）」がONのとき → 「任意の金額で入れる」は無効（灰色）＋理由「自動の伴走支援費が入っているため」。
  - 任意行がONのとき → 自動の「伴走支援費を含める」は無効。
  - 両方OFFが初期状態。切り替えるときは、もう一方がOFFであることを先に要求する（自動で消さない）。
- 修正で開いた出荷：すでに `support-fee` がある（Webからの申込で自動に入っている）→ 任意行の欄は無効で、理由を表示。
- **サーバー側でも同じ検査**（画面だけに頼らない）：保存時に `support-fee` が2行以上なら拒否。実装場所は出荷の保存まわり（supply.js の保存処理と、Firestore ルールまたは Functions）を実装時に確認。

### 3.3 入力欄（出荷モーダル・`shipSubsidyWrap` の下に並べる）
- チェック「伴走支援費を任意の金額で入れる」
  - 金額（税込・円・整数・1円以上）
  - 品名（初期値「伴走支援費」）
  - メモ（任意・内部用：例「先方のリーダー購入費を差し引いた額」）
- 表示条件：事業所へ直接請求する出荷（direct）のみ。認定事業者への直送（卸）は対象外（自動行と同じ）。
- **商品が0行でも保存できること**（ナガヨシ様のケース）。**調査済み（2026-11-09・supply.js の `saveShip`）**：保存の検査は `resolveShipItems()` の結果が空でないことだけ（「数量を入力してください」）。この結果には伴走支援費の行も入る（`productItems.concat(subsidyExtraItems())`）ので、**任意行を同じ経路で足せば、商品0行でも保存できる**。在庫を使う商品が無ければ「出荷元の保管場所」も不要（`stockItems(items).length` が0）。
  - 残る確認：商品が0行の出荷を「依頼済」にして倉庫へ出荷指示を投稿してしまわないか（出す荷物が無い）。`saveShipEdit` と出荷指示の投稿条件（ship-flow.js）を実装時に確認し、必要なら「物の出荷なし（伴走支援費のみ）」では指示を投稿しない／発送の工程を飛ばす。
- ロック：自動行と同じ（`moneyIds` に新しい欄を足す。依頼済み・発送済みなど金額がロックされる状態では編集不可）。

### 3.4 請求書・合計・助成金の内訳
- 合計（`updateShipTotal`／`invoiceTotals`）は items の合計なので、任意行も自動で含まれる。
- 請求書／領収証は B（伴走支援費・接続サポート等経費）に入る。「助成金の申請額＝A＋B」の表示もそのまま成り立つ。
- 助成金上限の超過チェック：任意行の金額と、同じ案件のカードリーダー購入費（A）の合計が上限を超えるなら**警告**を出す（止めない）。上限は案件の `subsidyCategory` から引く（福祉用具の other は1台あたり42,000円税込など。要綱を実装時に確認）。

### 3.4b 上限の扱い（推奨案・確認待ち）
- **上限を超える金額は入力不可**（警告ではなく、保存できない）。理由：伴走支援費は「助成金上限 − カードリーダー購入費」を超えると事業所の申請額が上限を超え、後から直せない（請求書を出した後は訂正が重い）。
- 上限の求め方：上限（案件の助成区分から。福祉用具の other は1台 42,000円税込など・要綱で確認）− カードリーダー購入費（A）。
- 問題：ナガヨシ様のように**先方が他で買ったリーダー**の購入費は、システムに入っていないので A を知らない。→ 欄を1つ足す：
  - 「先方が購入したカードリーダー費用（税込・任意）」。入れると「上限 − その額」が上限になる。¥30,200 の根拠（42,000 − 購入費）も出荷に残る。
  - 入れない場合は、上限＝助成区分の絶対上限（それ以上は入力不可）。
- 画面：金額欄の下に「入力できる上限：¥◯◯」を常に表示。超える数字を入れると赤字で理由を出し、保存ボタンは無効。
- サーバー側でも同じ検査（画面だけに頼らない）。

### 3.5 記録・監査
- 保存時に案件へ活動を1件足す：「伴走支援費を任意の金額で設定（¥30,200）・理由：…」。
- 誰がいつ入れたかを残す：行に `manualBy`（メール）・`manualAt`。

### 3.6 影響が出ない／出る場所
- 出ない：在庫（nonStock）、AB Circle への発注、Web申込の自動明細（Functions の `shipmentItemsFromQuote`）。
- 確認が要る：①出荷一覧・出荷依頼の投稿文に伴走支援費の行がどう出るか ②マニュアル（admin/manual.html）に1段落足す ③練習モード（practice-stubs.js）に同じ欄を出すか。

## 4. 実装の順序（案）
1. 現状の確認：商品0行で保存できるか／保存処理の検査の場所（半日以内の調査）。
2. データと検査：`manual` の印、排他の検査（画面＋サーバー）、単体テスト（scripts/test-ship-flow.mjs に追加）。
3. 画面：入力欄・無効化・合計の更新・ロック。
4. 請求書／領収証の表示確認（A/B区分・品名）。
5. マニュアル・活動記録・リリース前チェック（`/リリース前チェック`）。
