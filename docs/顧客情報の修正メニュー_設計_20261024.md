# 顧客情報（事業所）の修正メニュー 設計案（2026-10-24・案・未実装）

依頼: 藤田さん（PM・2026-10-24 9:31）
> CRMの重複案件が多い問題で、案件画面で整理できることは知っている。顧客情報画面に修正メニューを置いてほしい。例えば、法人で登録されているものを事業所として登録し直したり、法人⇔事業所の親子関係を付けたり。

## 1. いまの作り（実コード・実データで確認）

- 「事業所」画面（`offices.html` / `offices.js`）は**一覧と案件の展開だけ**。編集・統合のボタンは無い。
- データ: `offices/{id}` は**平たい1件**（`corpName`（法人名の文字列）・`officeName`・`address`・`phone`）。**法人という実体は無く**、法人名は文字列で持っているだけ。
- 案件 `cases` は `officeId` で事業所を指し、`officeName`・`corpName` を**写しとして**持つ（表示・通知・見積もりがこの写しを使う）。
- 統合できるのは**案件どうし**（案件画面の「この案件に統合」）だけ。事業所どうしの統合は無い。

実データ（2026-10-24・本番）:

## 2. 方針（推奨）

**3つの段階に分け、まず「直す」「まとめる」を出す。親子関係（法人の実体）はその次。**

| 段階 | できること | 藤田さんの例との対応 |
|---|---|---|
| **1. 事業所の編集** | 事業所名・法人名・住所・電話を直す。直したら、その事業所の案件の写し（`officeName`/`corpName`）も一緒に直す | 「法人で登録されているものを事業所として登録し直す」＝事業所名を正しい名前に、法人名を法人に |
| **2. 事業所の統合** | 重複した事業所を1つにまとめる。案件の `officeId` を残す側へ付け替え、消える側は「統合済み」にして一覧から隠す（データは消さない） | 重複案件の根本（事業所が2つある）を片付ける |
| **3. 法人と事業所の親子** | 「法人」を1件として持ち、事業所をその下に付ける。事業所画面を「法人 ▸ 事業所 ▸ 案件」で見られるようにする | 「法人⇔事業所の親子関係」 |

段階1・2だけで、いま困っている重複はほぼ片付く。段階3はデータの形を変えるので、1・2で名前と重複を整えてから入る方が安全。

## 3. 画面

事業所画面の各行に「…」メニューを足す（閲覧のみの人には出さない）。

- **編集**: 事業所名・法人名・住所・電話。保存前に「この事業所の案件 N 件の表示名も変わります」と出す。
- **ほかの事業所と統合**: 候補（同じ名前・同じ電話・同じ住所）を上に出し、検索でも選べる。左右に並べて、どちらを残すか・どの項目を残すかを選ぶ → 確認 → 実行。
- **（段階3）法人に付ける／法人を変える**: 法人を検索して選ぶ。無ければその場で法人を作る。
- 画面上部に「重複の候補」の件数バッジ（31組）と、絞り込み「重複の候補だけ」。

## 4. データと処理

### 段階1・2
- 統合は**1回の Callable Function（`mergeOffices`）でサーバーがまとめて行う**。画面から何十件も書くと途中で失敗したとき半端な状態が残るため。
  - 付け替えるもの: `cases.officeId` と写し（`officeName`/`corpName`）、`leadTokens.officeId`（問い合わせ→申込の継続で使う）
  - 消える側の事業所: `mergedInto: 残す側ID`・`archived: true`・`mergedAt/By`。**削除しない**（後から理由を追える・元に戻せる）
  - 各案件の対応記録に「事業所を〇〇に統合（実行者）」を残す
- 編集の写しの更新も同じく Callable（`updateOffice`）で、事業所と案件をまとめて書く。
- 権限: 管理者・スタッフ（案件の統合と同じ）。閲覧のみ・練習生は不可（サーバーでも確認）。
- 見積もり・請求書・出荷・承諾書は**発行した時点の宛名のまま変えない**（発行済みの書類の記録を書き換えないため）。

### 段階3（法人の実体）
- 新しいコレクション `corporations/{id}`（`name`・`corpNumber`（法人番号・任意）・`address`）。事業所に `corporationId`。
- `offices.corpName` は表示のため残し、法人を直したら写しとして更新する（既存の画面・通知・見積もりをそのまま動かすため）。
- 移行: 法人名の文字列で事業所を束ねて法人を自動で作る**案を先に一覧で出し**、次田さんか藤田さんが確認してから実行（表記ゆれ「社会福祉法人 〇〇」「(福)〇〇」は自動では束ねない）。

## 5. 練習モード・テスト

- 練習モードでは同じ処理を練習DBに対して行う（`practice-stubs.js` に `mergeOffices`/`updateOffice` を足す）。
- テスト: 統合で案件の付け替え漏れがない（件数一致）／二重実行しても壊れない／閲覧のみ・練習生は拒否／発行済みの見積もり・請求書の宛名が変わらない／統合済みの事業所が一覧に出ない／問い合わせの継続トークンが残す側を指す。
- 本番は Functions → ルール → Hosting の順。統合は取り消しが重いので、出す前に練習モードで藤田さんに触ってもらう。

## 7. 確定設計（段階1・2）— 2026-10-24 次田さん「進めて」・§8 は推奨どおり

| 発見 | 対策 |
|---|---|
| `findActiveCase`（functions/index.js:220）は**事業所名の完全一致**で動いている案件を探す。名前を直すと、旧名で来た次の問い合わせが新しい事業所・案件を作り、重複が再発する | 事業所に **`aliases`（旧名・統合で消えた側の名前）** を持たせ、`findActiveCase` は「案件の officeName」か「その事業所の aliases」のどちらかが一致すれば同じとみなす |
| 継続トークン `leadTokens.officeId` が統合で消える側を指したまま残る。次の見積もりが消えた事業所に付く | 統合でトークンの officeId も付け替える。加えて見積もり作成時に `mergedInto` をたどって残る側に読み替える（最大5段・循環は止める） |
| 事業所画面は offices を全件出す。統合済みも行として残る | `mergedInto` がある事業所は既定で隠す（「統合済みも表示」で出せる） |

### 7.1 Callable の約束（サーバーと画面の共通の契約）

すべて `region: asia-northeast1`・`requireStaff(request, {allow:"editor"})`（管理者・スタッフ。閲覧のみ・練習生は拒否）。

**`updateOffice({ officeId, patch })`**
- `patch` に入れてよいのは `officeName`・`corpName`・`address`・`phone`・`postalCode` だけ（他は invalid-argument）。文字列・前後空白を除く・各200字まで。`officeName` は空にできない。
- 統合済み（`mergedInto` あり）の事業所は編集できない（failed-precondition）。
- 事業所名か法人名が変わったら、その事業所の**全案件**（対象外も含む）の `officeName`/`corpName` を新しい値に。旧事業所名は `aliases` に足す（重複なし）。
- 事業所名が変わったときだけ、各案件の対応記録に「事業所名を変更：旧 → 新（実行者）」。
- 戻り値 `{ ok:true, casesUpdated:N }`。

**`mergeOffices({ fromId, toId, keep })`** … from を to に統合（from が消える側）
- `keep`: `{ officeName, corpName, address, phone, postalCode }` の各項目に `"from"|"to"` を指定（省略は `"to"`）。残す側の値を決める。
- 拒否: from==to／どちらかが存在しない／to が統合済み／from が別の事業所に統合済み。from が同じ to へ統合中（`mergeStatus:"running"`）なら**続きから再開**（何度呼んでも同じ結果）。
- 手順（途中で落ちても再実行で完了する形）:
  1. トランザクション: from に `mergedInto: toId`・`mergeStatus:"running"`・`mergedAt`・`mergedBy`・`archived:true`。to に keep で選んだ値と `aliases`（to の旧名＋from の事業所名＋from の aliases）を書く。
  2. `officeId == fromId` の cases・quotes・shipments・leadTokens を 400件ずつ付け替え。cases は `officeName`/`corpName` も残す側の値に。from に `mergedCaseSnapshots`（{caseId:{officeName,corpName}}）と付け替えたID一覧（`mergedRefs: {cases:[],quotes:[],shipments:[],leadTokens:[]}`）を残す（取り消し用）。
  3. 各案件の対応記録「事業所を統合：〇〇（from）→ 〇〇（to）（実行者）」。
  4. from の `mergeStatus:"done"`。
- 戻り値 `{ ok:true, moved:{cases,quotes,shipments,leadTokens} }`。

**`unmergeOffice({ fromId })`** … 統合の取り消し
- from が `mergeStatus:"done"` のときだけ。`mergedRefs` に記録したもので、**いまも officeId == toId のもの**だけを from に戻す（統合後に別へ動かしたものは触らない）。cases の名前は `mergedCaseSnapshots` に戻す。
- from の `mergedInto`/`mergeStatus`/`archived` を消し、`unmergedAt`/`By` を記録。to の aliases から from の名前は外さない（害がないため）。
- 戻り値 `{ ok:true, restored:{...} }`。

### 7.2 サーバー側のその他の変更
- `findActiveCase(email, officeName)`: 候補案件ごとに、`c.officeName === officeName` または `offices/{c.officeId}.aliases` に officeName が含まれる、で一致とみなす（事業所は候補の分だけ読む）。
- 見積もり作成（`createOrUpdateMitsumoriQuote`）: `lead.officeId` と既存案件の officeId を、`mergedInto` をたどって残る側に読み替えてから使う。
- 判定ロジック（keep の検証・aliases の組み立て・付け替え計画・取り消し対象の選別）は **`functions/office-merge.js`（純粋関数・CommonJS）** に切り出し、`scripts/test-office-merge.mjs` でテストする（`accept-rules.js` と同じ流儀）。

### 7.3 画面（事業所画面）

- 統合の相手は候補を上に出す: 事業所名（空白・括弧を除いて同じ）・電話（数字だけで同じ）・住所（同じ）。下に検索。
