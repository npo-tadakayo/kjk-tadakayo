# 出荷の二段階化（「出荷を依頼する」→「発送済にする」）設計 — 2026-10-20

ブランチ: `crm-ship-request`（origin/main `1cca377` から）／依頼者: 藤田さん（博之）／決定: 次田さん 10/20「案B」
状態: **設計のみ。実装はこれから。本番反映は次田さんの承認後（rule05-3.5：プレビュー → verify → 昇格）。**

## 1. なぜ直すか
今の「発送済にする」は、押した瞬間に ①出荷が「発送済」になる ②在庫が引き落とされる ③出荷指示が Chat に投稿される が同時に起きる。
実際にセンターが発送する前に「発送済」になり、ボタンの名前と中身がずれている（藤田さん指摘）。

## 2. 新しい流れ
```
下書き(draft) ──「出荷を依頼する」──▶ 依頼済(requested) ──「発送済にする」──▶ 発送済(shipped) ▶ 請求済 ▶ 入金済
                  出荷指示を投稿               センターが発送したのを確認して押す        在庫を引き落とす・請求の起点
```
- **新しい状態**: `requested`（表示は「依頼済」）。保存するもの: `requestedBy`／`requestedByEmail`／`requestedAt`／希望出荷日（`shipDate`）／出荷元／レターパックの種類。
- **「出荷を依頼する」**（下書きの主ボタン）: 確認の画面（希望の出荷日・出荷元・レターパック）→ `requested` にして出荷指示を投稿。**在庫は引き落とさない**。
- **「発送済にする」**（依頼済の主ボタン）: 確認の画面（発送日・追跡番号は任意・出荷元）→ `shipped`・在庫を引き落とす・`dueRule:'net14'`・押した人を記録。**出荷指示は投稿しない**。
- **依頼済のそのほかの操作**: 「出荷指示を再送」「依頼を取り消す（下書きへ戻す）」。
- **すでに届いている出荷**（伴走支援が済んだ案件など）: 下書きに小さなボタン「すでに発送済（記録のみ）」を残し、依頼を経ずに `shipped` へ。出荷指示は送らない（今の「出荷指示を送らない」チェックの代わり）。
- **直接登録（出荷の新規作成）**: 「登録して出荷を依頼する」→ `requested` で作成して投稿。チェック「すでに発送済として登録（指示は送らない）」で `shipped`。

## 3. 決めた既定（変えてよい）
| 項目 | 既定 | 理由 |
|---|---|---|
| 在庫の引き落とし | **発送済にしたとき** | 次田さん案B「在庫・請求の起点を発送済へ」。依頼から発送までの間は在庫がまだ数に入っているので、依頼の時点で在庫不足なら警告（止めない）、発送済の時点で不足なら止める |
| 依頼済の出荷の修正 | 送付先・数量とも直せる。数量・送付先を直したら「出荷指示を再送しますか？」と聞く | センターが古い内容で動かないように |
| 依頼済のキャンセル | 在庫は戻さない（まだ引いていない）。出荷指示を取り消す連絡は人が行う | 自動で取り消す仕組みは作らない |
| 既存データ | **変えない**（発送済・請求済の出荷はそのまま） | 移行不要 |
